# 多注塑件报价方案（探讨稿）

> 状态：待确认，未实施
> 日期：2026-09-10
> 起因：一张报价单只能报一个产品，无法处理「纯注塑 20 个件」和「开模 1 套 + 注塑 N 个件」

---

## 一、问题定义

用户提出的两类真实业务：

**场景 A：纯注塑代工（客户自带模具）**
- 不需要开模，只做注塑加工
- 有 20 个注塑件，每个件的**尺寸、重量、材料、数量都不同**
- 需要每个件单独算价，最后汇总成一张报价单

**场景 B：开模 + 注塑**
- 开模 1 套（或几套）
- 注塑件有很多个，每个件的参数也各不相同
- 模具费 + 各件注塑费，汇总成一张报价单

**共同点**：都需要「一张单里装多个可独立算价的对象」。

---

## 二、现状的结构性限制

当前模型是 **「一张报价单 = 一套参数 = 一个产品」**，有三处硬限制：

### 2.1 参数是扁平的、只有一套

`QuoteVersion.paramsJson` 是一个扁平对象：

```json
{ "腔数": 2, "单件重量": 0.18, "模芯长": 500, "原料单价": 12, "注塑数量": 5000 }
```

20 个件需要 20 套这样的参数，**没有地方放**。

### 2.2 计算结果只有一组

`ConfigCalcResult` 输出的是单个实例的结果：

```ts
{ lines: [...], mold: 56247.5, injection: 13090, unitCost: 2.62, injectionQty: 5000, total: 86186.5 }
```

无法表达「P-01 是 13,090，P-02 是 12,300……」这种逐件明细。

### 2.3 参数没有作用域

`CustomParameter` 只有 `group`（产品 / 商务 / 材料…），**没有说明这个参数属于模具还是属于件**。

后果：录入界面无法自动分组——填模具参数时不该看到「单件重量」，填件参数时不该看到「模芯长」。现在只能靠参数名让用户自己分辨。

---

## 三、方案：引入「报价单元」

### 3.1 概念模型

把报价单从「一个产品」升级为「一个项目」：

```
报价单（项目）
├── 公共参数（利润率、税率、运费区域）—— 整单一份
├── 模具清单（0 ~ N 套）
│   └── 每套模具：模具参数 + 模具费用项（scope = mold）
└── 注塑件清单（0 ~ N 个）
    └── 每个件：件参数 + 注塑费用项（scope = injection，perUnit）+ 数量
```

三种业务场景用同一套结构表达，不需要做不同的「报价单类型」：

| 场景 | 模具清单 | 注塑件清单 |
|---|---|---|
| 只开模 | 1 套 | 0 个 |
| 只注塑代工（场景 A） | 0 套 | 20 个 |
| 开模 + 注塑（场景 B） | 1 ~ N 套 | N 个 |

> 注：**一张单对应一种工艺**（注塑 / 压铸 / 双色 / 橡胶），工艺由模具类型决定，决定用哪套费用项。若同一客户要报注塑 + 压铸，开两张单。跨工艺混报在实务中罕见，且会让费用项定义失控。

### 3.2 参数作用域（关键改动）

`CustomParameter` 增加 `scope` 字段：

| scope | 含义 | 典型参数 | 填写次数 |
|---|---|---|---|
| `mold` | 模具相关 | 模芯长/宽/高、钢材单价、腔数、模具重量、运输箱尺寸、运费单价 | 每套模具 1 次 |
| `part` | 注塑件相关 | 单件重量、材料、成型周期 | 每个件 1 次 |
| `common` | 公共 | 利润率、税率、运费区域 | 整单 1 次 |

**这是录入体验的关键**：有了 scope，界面才能自动分组——模具卡片只显示 mold 参数，件行展开只显示 part 参数，底部只显示 common 参数。用户不会在填件的时候被模具参数干扰。

### 3.3 计算：不动引擎核心，加一层聚合

这是本方案**最重要的工程决策**——现有引擎 `calculateConfigured(items, params)` 算「一个实例」的能力是正确的，不必重写，只在外面套一层「多实例聚合」：

```
calculateConfigured(items, params)          ← 保持原样，算 1 个实例
            ↑
calculateQuoteProject({
  items,                                    ← 费用项定义（含 scope）
  common,                                   ← 公共参数
  molds: [{ code, name, params }],          ← 逐套调用
  parts: [{ code, name, qty, params }],     ← 逐个调用
})
            ↓
        聚合为一张结果
```

汇总口径：

```
模具小计 = Σ 各套模具的 mold 小计
注塑小计 = Σ 各件 (该件单件成本 × 该件数量)
小计     = 模具小计 + 注塑小计
利润     = 小计 × 利润率
税       = (小计 + 利润) × 税率
含税总计 = 小计 + 利润 + 税
```

**下游零改动**：新结果在顶层仍然输出 `total`，而所有金额读取都已经收敛到 `services/quoteTotal.ts` 的 `calcTotal()` 一个入口（后台管理、客户库、Dashboard 全走它）。只要 `total` 含义不变，这些地方一行都不用改。

### 3.4 数据结构与老单兼容

`paramsJson` 结构升级，**读取时按结构判断**，老单视为「1 个注塑件」：

```jsonc
// 老结构（已有报价单）—— 自动视为 1 个件
{ "腔数": 2, "单件重量": 0.18, "注塑数量": 5000 }

// 新结构
{
  "common": { "利润率": 0.1, "税率": 0.13 },
  "molds": [
    { "code": "M-01", "name": "洗衣机控制板模具", "params": { "模芯长": 500, "腔数": 2 } }
  ],
  "parts": [
    { "code": "P-01", "name": "旋钮", "materialCode": "ABS", "qty": 5000, "params": { "单件重量": 0.18 } }
  ]
}
```

老单**不改数据、不重算**，历史报价的金额保持冻结。只有新建的单用新结构。

### 3.5 录入体验（决定方案成败）

20 个件如果每个都填一整套参数（5~10 个输入框），就是 100~200 个输入框，用户必然放弃。必须靠这几点压住：

1. **表格化录入**——一个件一行，表格里只放关键列（件号 / 名称 / 材料 / 单件重量 / 数量 / 金额），点开某行才展开该件的全部参数
2. **材料从材料库选**——选「ABS」自动带出密度、单价、损耗率，不用手填三个数（依赖 4.3 决策）
3. **复制选中**——20 个件里常有一半是同材料同工艺的，复制后改重量和数量即可
4. **Excel 导入**——客户本来就有零件清单（件号、名称、材料、重量、数量）时，直接粘贴导入
5. **批量改数量**——多选后统一改数量

### 3.6 波及面清单

| 位置 | 影响 | 说明 |
|---|---|---|
| 计算引擎 | **加聚合层** | 核心 `calculateConfigured` 不动 |
| 报价单编辑器 | **重写** | 改成「模具卡片 + 件表格」 |
| 配置中心 | **中等** | 参数增加 scope 归属；费用项已有 scope 可复用 |
| Excel 导出 | **中等** | 改成「汇总页 + 逐件明细页」 |
| 客户分享页 | **中等** | 展示件清单汇总，不泄露分项成本 |
| 报价单详情页 | **中等** | 分模具段 / 件段展示 |
| 后台管理、客户库、Dashboard | **无** | 走 `total`，不用改 |

## 四、决策结论（已确认 2026-09-10）

### 决策 1：模具与注塑件的对应关系

**已定：并列 + 可归属。**

模具清单与件清单并列，每个件可选填「由哪套模具生产」。覆盖三种情况：

- 纯注塑代工：0 套模具 + N 个件
- 一套模具出多个件
- 一个项目开多套模具：1 ~ N 套 + N 个件

### 决策 2：一个件是否支持多个数量档位（阶梯报价）

**已定：暂不支持，一件一行。**

先把「20 个件能报价」这个核心问题解决。需要报多个量档时用多行变通
（如 `P-01-5000` / `P-01-20000`），界面上仍能对比单价。
后续若业务确有需要，再在「件 × 量档」二维表上迭代一版。

### 决策 3：件的材料从哪来

**已定：从材料库选择。**

件上带一个「材料」字段，从材料库（35 种预置）选择，自动带出密度 / 单价 / 损耗率。
与待办项「材料改全局引用」是同一件事——件引用全局材料，改一次价全公司生效。

### 决策 4：利润与税的口径

**已定：整单统一。**

一个项目一个利润率、一个税率，放在公共参数里。计算口径统一，客户看到的报价逻辑清晰，
也便于对账。不做按件单独设置。

## 五、实施路径（建议分四步）

| 阶段 | 内容 | 风险 |
|---|---|---|
| **1. 地基** | 引擎加聚合层 `calculateQuoteProject`；参数加 `scope` 字段；新数据结构 + 老单兼容读取 | 低。纯新增，不动现有计算 |
| **2. 配置** | 配置中心支持给参数指定 scope（模具 / 件 / 公共）；预置模板按 scope 重排 | 低。需数据迁移（补 scope 默认值） |
| **3. 编辑器** | 报价单编辑器改成「模具卡片 + 件表格」，含复制 / 批量 / 展开行 | 高。改动最大，需充分验收 |
| **4. 输出** | Excel、分享页、详情页适配多件展示 | 中。Excel 模板要重做 |

每步都按既有流程走：**写迁移脚本 → 本地验证 → pg_dump 备份 → 上线 → 浏览器验收**。

---

## 六、与之前方案的关系

本方案是此前「信息架构改造」的延续，不是推翻：

- 主导航 3 项（报价单 / 客户 / 设置）不变
- 「材料改全局引用」这项待办，与本方案**决策 3** 是同一件事——件从材料库选材料，天然要求材料是全局一份
- 「商务条款抽全局模板」仍然独立，不受本方案影响

建议顺序：**先做本方案的地基（阶段 1+2），再回头做材料全局引用**——两者合流后改动更省。
